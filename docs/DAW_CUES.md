# Independent cue mixes and hardware outputs — 0.82.0

## Workflow

Reference Studio adds **Headphone cue mixes and hardware outputs**. Load stopped cue draft, enter a name and Add cue. Select the cue to edit its level, stereo balance, mute and physical output indices. Indices are zero-based: 0/1 normally mean the interface's first stereo pair. The app proposes an unused pair; choose a pair supported by your interface and distinct from Main and the other cues. Up to four independent stereo mixes are available.

Choose a source type, select its track/bus/aux or physical input channels, and Add source to cue. Each send has its own gain and balance. Track Pre taps audio after its own instrument/inserts but before global track alignment and strip controls; it ignores track fader/mute/solo, providing a useful performer balance. Track Post follows the strip and common track alignment. Submix taps its processed bus output, Aux its processed return including return gain, and Main the complete main chain. Mono input duplicates one physical channel to both ears; Stereo input takes two independent channels. Raw input taps are silent until audio input is enabled and its callback bridge is ready. They can monitor an armed dry input even when main input monitoring is off.

Align source delays delays each send to the longest source path in that cue. Turn it off only when you deliberately want sources at their own timings. A cue using only a raw input or zero-latency Pre tap adds no DSP delay; device/OS buffers, the input bridge, converters and the acoustic/electrical path still add latency. The panel reports maximum source delay in frames, not a measured round trip. Use the calibration workflow for real recording alignment.

Recording click enables the existing audio-recorder count-in/metronome in this cue. Its stereo weights follow the cue's sample-by-sample gain/balance/mute controls; when alignment is enabled the click is delayed to the cue's longest source path. It remains a monitor overlay and is excluded from dry/rendered-track recording taps. The recorder's global click/count-in settings still determine when clicks are generated. This does not add a new MIDI-recorder count-in system or a general always-running transport metronome.

Apply prepared cue mixes stops/snapshots playback, verifies the baseline and complete candidate, prepares it and records one project-history edit. Undo/Redo restores all cue settings. Play opens the required physical output channel count with Main and the cue pairs. A device that cannot provide the selected rate/map/count reports an error; it does not fold a performer mix into another output. Cues also work during MIDI and audio recording, including a callback that crosses the count-in/play boundary. Use the engine-parameter sliders for live cue/send levels while playing, and Save to persist current values. Peak meters appear with the other prepared mixer meters.

## Public API and example

`studio::cues::{Cue,Send,Source,validate,input_channels}`. Document.cues is an optional vector. Stable cue/send IDs give automation keys cue.ID.gain/.pan/.mute and cue.ID.send.SENDID.gain/.pan. Send IDs survive list reorder; removing a send/cue cleans its obsolete normalized values and lanes through the stopped mixing draft. `mix_graph::Draft::new/apply` handles typed cue edits too, materializing saved live values into editable fields and rejecting changed baselines.

`PreparedSession::output_bus()` and `Controller::output_bus()` return the prepared ChannelBus bank when cues exist. Logical channels 0/1 contain the main render, followed by one stereo pair per cue in document order. `cue_latencies()` reports each cue's maximum source latency; for an unaligned cue different sources retain their individual delays. Custom native device builders pass this Arc as OutputEngine.output_bus and set DuplexRoute.cue_outputs in the same order. Primary hardware output uses the final stereo engine buffer; extra pairs read their logical bank channels. Existing builders without cues set output_bus to None. DuplexOptions similarly gains output_bus/cue_outputs; default construction preserves the old stereo path.

`device::OutputMap::new/render/frame` validates and applies the same physical mapping used by the native callback. It clears unassigned channels, rejects overlaps/out-of-range destinations and a mismatched/missing bank, sanitizes nonfinite primary samples and clamps device output. It supports 2–64 hardware channels and up to four extra pairs. Virtual tests can use it without opening an interface. DevicePreferences retains optional cue_outputs under its existing duplex route, chooses a configuration that reaches the highest selected port, and keeps the processing spec stereo while hardware channel count grows.

`midi_recording::prepare_low_latency_with_inputs` accepts the physical input Setup so input cues remain available during MIDI recording. Existing preparation APIs retain their signatures and no-input defaults. The reference builder writes that same input bus before processing. Core ChannelBus gains begin/offset/write_at/add_sample for prepared outer-callback publication and monitor overlays; one callback owns writes. Begin clears visible frame count, write_at publishes contiguous ranges at a checked origin, and missing/unpublished frames read as zero.

Run `cargo run -p soniclaw-daw-cues -- /tmp/soniclaw-cues-new`. It creates four distinct mixes with Main muted, maps them into a virtual twelve-channel device, checks unmapped silence/overlap errors and negotiation at the highest selected port, verifies absent-input silence, source-delay alignment and internal automation partition invariance, crosses a count-in boundary, checks cue click balance/delay, and saves/undoes/reopens the settings. It measures cue/mapping callback allocations and emits report.json. The virtual device does not represent physical acceptance.

## Timing, ownership and persistence

Pre taps retain a prepared copy before the track's global alignment delay. Post/bus/aux/Main taps use their actual path delays from the existing compensated mixer. Each cue owns independent prepared edge delays, buffers, smoothed controls and meter exchanges. No send rewires the main path. Raw input is read from the prepared physical bus using the callback's current sub-block origin; no decoding, device selection or allocation happens in cue processing.

Studio's musical clock and automation may subdivide a block. The publication bank writes each subrange at its outer-frame coordinate. Audio recording similarly preserves count-in/play subranges and their independent input/output origins. A second prepared bank carries per-sample cue master weights for the recorder click; the click's prepared delay and gain/balance/mute therefore follow the cue without retrospectively applying a block-final value. Native callbacks begin a fresh visible output range before invoking the engine, so suspension/failure cannot replay a prior bank. Built-in recording wrappers restore outer offsets after subdividing. Custom wrappers that subdivide a bank-producing processor must maintain/reset these origins too; external Engine.process_automated wrappers are not automatically bank-aware. Use Studio's internal automation for this workflow.

Cue topology changes stop/reprepare in reference Studio. Controller.replace explicitly rejects replacement when either session has cue outputs, avoiding stale device-bank ownership and unblended alternate cue graphs during a stereo graph crossfade. Parameter automation and live fader edits remain supported on the prepared handles. All model edits, validation, allocations, native preparation, saving and retirement occur on the appropriate control/owner thread. The driver and cue renderer use bounded scratch and atomic exchanges.

Document remains schema 1 with optional cues omitted when empty; Project remains schema 3. Existing empty documents and device preferences default to no cues, preserving prior playback and legacy identity derivation. Older strict readers may reject populated new fields. Cue names/routes/sends/click choices and parameter values persist; UI drafts, meter peaks and device callback buffers do not. Physical output numbers are song settings; they may require adjustment when moving the song to a different interface. Device preference save retains the output map for custom hosts. Global output enable/mute gates all physical outputs, and ordinary device bypass controls the primary stereo path while cue mixes retain their defined sources.

## Bounds, errors and evidence

Four cues, 32 sends/cue, two channels/cue and 64 physical channel indices. Each input tap is mono/stereo. Existing 32-track/four-aux/eight-submix/4096-parameter limits apply. All cue/source controls are finite with gain 0–4 and balance -1–1. Cue names are nonblank up to 256 bytes; cue and send IDs follow the existing bounded identity grammar. Compensation is bounded to 262144 frames/path and shares the existing total prepared delay-storage budget, including cue click delays. Cue sums can clip and are clamped at the device boundary; these limits do not guarantee a machine's real-time CPU capacity.

Missing/invalid source identities, invalid/duplicate send/cue IDs, missing bus/aux references, overlapping cue pairs, unsupported physical output maps/rates/counts, out-of-range inputs, wrong bank shape, invalid controls, excessive delay/parameter storage and stale drafts reject without adopting a partial project. Raw input taps intentionally produce silence when no physical input bus is supplied or ready. Deleting a track/bus still referenced by a cue requires removing/retargeting that send first. Callback errors clear or leave unpublished output frames silent and update existing telemetry; original media and the main arrangement are not modified by audition or routing.

Executed evidence includes the runnable example/regression, core publication-range/overlay tests, device mapper sanitation/mute/overlap tests, headless desktop cue creation/apply/undo, full-workspace/all-target/all-feature Clippy and warnings-denied Rustdoc. Actual counts/logs are recorded in the adjacent release validation. Physical routing/headphone monitoring, converter/interface latency, third-party native products and Windows/macOS runtime remain pending. This is a source/software workflow release, not a hardware certification.
